## B-P1-01 — 새 release branch 규칙과 정식 태그 명령의 대상이 충돌함

- 심각도: **P1**. Disposition: **OPEN**.
- 위치: [release](../../../runbooks/release.md) 46행의 새 branch 규칙, 54~56행 준비 절, **137~139행 정식 발행 명령**, 171행 체크리스트. [agent-workflow](../../../runbooks/agent-workflow.md) 219·243행의 main 대상 PR/merge 확인도 새 예외와 연결되지 않았다.
- 근거: ADR-014 결정 6과 release §2.1은 보존 후보에서 갈라진 release branch의 PR·commit을 태그 대상으로 정한다. 그런데 §3.5는 실제로 `git switch main && git pull --ff-only origin main` 뒤 commit 인자 없는 `git tag -a tokens-v0.1.0 ...`을 실행한다. §3.1과 체크리스트 역시 main merge를 요구한다. 새 앞 문장만으로 실제 명령이 다른 ref를 선택하는 문제는 해소되지 않는다.
- 실패 시나리오: tokens 후보 C를 보존하고 main에서 UI/Python 후속 개발을 진행한다. 뒤늦은 tokens rc 검증에서 결함을 발견해 release branch에서 C를 수정하고 새 rc·소비자 검증을 통과한 R을 만든다(ADR-014가 허용하는 경로). R에서 정식 metadata/lock을 만들고 검증한 뒤 §3.5 명령을 그대로 실행하면 태그는 R이 아닌 main의 M을 가리킨다. main에는 해당 rc 수정이 없을 수 있다. Git 태그 설치와 Release 자산이 서로 다른 소스를 나타내고, 불변 태그를 이미 push한 뒤에는 같은 버전으로 정정할 수 없다. UI/Python 절차에 같은 정식 단계가 적용되면 main의 0.2 개발 소스를 이전 0.1로 가리킬 위험도 생긴다.
- 재현: 문서의 정식 발행 절에서 main 전환과 명시 source 없는 tag 명령을 읽기 전용 스크립트로 추출·확인했다. 실제 태그·Release는 만들지 않았다. 이는 Git 조작 성공의 주장 대신 명령이 선택하는 ref의 정적 대조다.
- 영향: 검증 commit과 발행 태그의 불일치, 잘못된 구버전 발행 및 복구 불가한 같은 버전 재발행 압력. T-015의 “후속 minor가 앞선 후보를 덮어쓰지 않음·태그 불변” 수용 기준을 충족하지 못한다.
- 권고: §3.1·3.5·체크리스트·일반 workflow의 릴리스 예외를 같은 대상 branch/commit으로 통일한다. PR base와 merge commit을 명시하고 최종 source commit·package metadata·자산 digest를 확인한 뒤 그 commit을 명시적으로 태그하라. main으로 돌아가는 명령은 정식 태그 단계에서 제거한다. 다음 minor가 진행된 main과 수정 rc branch가 다른 상황을 문서 검증 사례로 고정한다.

## B-P2-02 — 0.2 릴리스가 분기할 보존 소스와 책임 task가 정의되지 않음

Python T-311도 같은 문제다.
- 재현: 두 release task의 전체 실행 범위·선행과 ADR/runbook의 후보 tag 형식을 대조했다. 0.2 후보 보존·release branch 생성 주체/기준 commit에 대한 연결이 없다. 실제 패키지는 아직 없으므로 잘못된 패키지가 만들어졌다는 주장은 하지 않는다.
- 영향: 다음 에이전트가 순차 계획만으로 후속 minor 릴리스를 준비할 수 없고 버전만 올린 불완전한 소스 선택을 유발한다. 기존 모듈 목록·설치 검사가 있다면 발행은 막히지만 그 전에 해결해야 하는 계획상 공백이다.

## B-P2-03 — 과거 후보 branch와 현재 main 원장의 완료 기록 왕복이 빠짐

- 심각도: **P2**. Disposition: **OPEN**.
- 위치: [release](../../../runbooks/release.md) 40~46행의 후보/branch 생성, 148~158행 후속 기록; [통합 계획](../../../plan/integration-plan.md) §2·§4; 관련 [task 규칙](../../../tasks-rule.md) 74~78행과 `validate_plan.py` 141~142행.
- 근거: release §2.1은 버전·lock뿐 아니라 §3의 릴리스 기록 변경도 과거 후보에서 갈라진 branch에 둔다. §3.6은 task·resume·journal·CHANGELOG 갱신을 요구하지만, 현재 main의 선행 완료 상태를 release branch에 가져오거나 릴리스 완료 evidence를 main 원장으로 돌려보내는 PR 절차는 없다. 일반 workflow는 origin/main 기반 단일 branch만 전제로 한다.
- 실패 시나리오: 후보 tag 생성 전 검증 source C에는 T-109a가 아직 IN_PROGRESS이고 T-010a가 BLOCKED다. 후보 tag를 확인한 뒤 main에서 T-109a를 닫고, 나중에 외부 검증 evidence로 T-010a도 닫는다. C에서 만든 tokens release branch가 T-109 발행 후 그 branch의 T-109만 DONE으로 갱신하면 해당 branch의 오래된 두 선행 상태가 남아 plan CI가 실패한다. 반대로 release branch에서 선행 기록까지 맞춰 닫아도 main에는 T-109 BLOCKED가 남아 후속 task가 열리지 않는다. release branch를 main에 그대로 합치는 것은 이전 패키지 metadata·lock과 최신 구현을 섞을 수 있으므로 문서 전용 인계가 필요하다.
- 재현: 실제 101개 task를 `validate_plan.details()`로 읽어 메모리에 두 branch 상태를 만들었다. T-109a의 모든 선행은 DONE, C의 T-109a는 IN_PROGRESS·T-010a는 BLOCKED로 두고 main만 두 상태를 DONE으로 진전시켰다. release branch의 T-109를 DONE으로 바꿔 실제 `check_graph()`를 호출한 결과 `T-109: DONE인데 선행 T-109a 미완료`, `T-109: DONE인데 선행 T-010a 미완료` 두 오류를 확인했다. main 사본의 T-109는 BLOCKED였다. 이는 미래 상태의 모델 검사이며 저장소 파일·branch를 수정하지 않았다.
- 영향: 실제 릴리스가 끝나도 정본 원장의 선행이 닫히지 않거나, 과거 branch에서 기록을 닫으려다 필수 CI와 충돌한다. 다음 에이전트가 현재 main에서 이어갈 수 있는 완료 인계가 불완전하다.
- 권고: source/산출물 기준선과 현재 실행 원장의 위치를 명시한다. release branch의 선행 evidence를 어떻게 확인·반영할지, 발행 뒤 main에 어떤 문서·상태만 별도 PR로 되돌릴지, old package/lock을 main에 되돌리지 않음을 정한다. 후보 tag는 고정 소스를 유지하고 이후 생성되는 evidence·closure commit은 별도 참조로 연결한다. 양 branch의 plan 검증과 main 후속 task READY 전환까지 절차에 포함한다.
