## A-P1-01 — release branch 정책과 정식 태그 명령이 서로 다른 commit을 선택한다

- 심각도: **P1**.
- Disposition: **OPEN**.
- 위치: [release runbook](../../../runbooks/release.md) 46행, 54행, 137~142행, 171행. 근거 정본: [ADR-014](../../../adr/014-common-implementation-without-registry-publishing.md)의 후보 보존·늦은 릴리스 결정.
- 근거: 새 §2.1은 rc와 정식의 버전/lock 변경 및 tag 생성 대상이 후보에서 분기한 release branch라고 명시한다. 그런데 §3.1은 릴리스 변경이 모두 main에 merge됐는지 확인하고, §3.5는 `git switch main && git pull --ff-only origin main` 직후 별도 commit 인수 없이 정식 tag를 만든다. 체크리스트 첫 행도 main merge 완료를 요구한다.
- 실패 시나리오: T-212a 또는 T-310a의 0.1 후보를 보존하고 main에서 0.2 구현을 진행한다. 외부 승인이 늦게 와서 0.1 release branch의 rc를 검증한 뒤 §3.5를 그대로 적용하면 HEAD가 main으로 바뀐다. 이어지는 annotated tag는 검증한 0.1 release commit이 아니라 다음 minor를 포함한 main을 가리킨다. commands는 tokens 예시이지만 문서 자체가 tokens/ui/py 공통 절차다.
- 재현: candidate의 §2.1과 §3.1/3.5/§5를 행 단위로 읽고 위 HEAD 전환을 추적했다. 실제 tag/Release 생성은 수행하지 않았다. `git tag -a <name>`에 commit 지정이 없는 상태에서 앞 명령이 선택한 HEAD를 대상으로 한다는 명령 구조상 충돌이다.
- 영향: 현재 규범끼리 충돌해 순차 실행 에이전트가 잘못된 source에 과거 버전 태그를 만들 수 있다. 검증 artifact와 태그 source의 대응도 깨진다. 문서 선두의 일반 지시만으로 실행 블록의 반대 지시를 남겨둘 수 없다.
- 권고: §3.1·§3.5·체크리스트를 §2.1에 맞춰 일괄 정렬한다. 릴리스 branch의 리뷰·CI 완료 commit을 선택하고 version·검증 SHA와 tag target을 확인하는 실제 절차로 바꾼다. main merge/checkout 요구를 제거하고 rc→정식도 같은 source 경로인지 확인한다.
