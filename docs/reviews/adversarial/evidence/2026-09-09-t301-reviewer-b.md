## Findings

### B-P1-01 — 예외 `reason`의 필수 정합 task ID가 정본과 validator에서 보장되지 않음

- 심각도: P1
- 위치: `docs/standards/openapi.md:186`, `tools/openapi_exceptions.py:370-375`, 현재 `docs/standards/openapi-exceptions.yaml`의 여러 entry
- 근거: §6.1은 `reason`에 사실 근거와 정합 task ID를 **반드시** 포함한다고 명시한다. 그러나 validator는 `reason`을 비어 있지 않은 문자열인지(`tools/openapi_exceptions.py:373-375`)만 검사한다. 현재 46개 중 20개는 `T-<번호>`·`ADR-<번호>`·`O-<번호>`·`D-<번호>`조차 없는 상태다. 예를 들어 geo `M3`(YAML 20~24), geo `N5`(34~38), pinvi `S5`(99~103), concierge `S3`(220~224), ktdm `M7`(257~261), weather `M6`(331~335)는 `oa`/`be` 절만 있고 정합 task ID가 없다.
- 재현: 아래 명령 결과가 `missing_provenance 20`을 출력하고도 `load_registry`는 exit 0이다.

  ```text
  python -B -X utf8 - <<'PY'
  from datetime import date
  import re
  from tools.openapi_exceptions import load_registry
  r = load_registry(as_of=date(2026, 9, 9))
  bad = [e for e in r["exceptions"] if not re.search(r"(?:T|ADR|O|D)-\d+", e["reason"])]
  print(len(bad))
  PY
  # 20
  ```

- 영향: 예외가 어떤 이관 task에서 닫히는지 추적할 수 없는 항목도 생성 Markdown·후속 매니페스트에 정상 등록된다. 분기 감사와 consumer 이관 순서가 정본의 필수 provenance 계약을 우회하므로 감사 가능성과 task 실행 가능성이 깨진다. 빈 값·미지 rule만 막는 검사는 이 누락을 조기에 차단하지 못한다.
- 권고/disposition: `reason`에 실제 `T-NNN`을 필수로 하는 validator와 회귀 시험을 추가하고, 20개 entry의 근거와 task를 직접 보강한다. 현재 candidate에서는 `OPEN`이며 P1이므로 `BLOCK`이다.

### B-P1-02 — SHOULD 미채택을 예외로 등록하지 않는다는 규칙과 YAML 10건이 충돌

- 심각도: P1
- 위치: `docs/standards/openapi.md:192-199`(특히 §6.2 5번), `docs/standards/openapi-exceptions.yaml:55,83,99,127,141,148,171,178,220,308`, `tools/openapi_exceptions.py:367-379`
- 근거: §6.2 5번은 계층 3 `S1~S13` 미채택을 예외로 등록하지 않고 소비자 매니페스트에 “미채택”으로 보고한다고 정한다. 예외는 타 저장소를 깨뜨리는 외부 계약인 경우만 허용한다. 현재 registry validator는 모든 유효 rule을 같은 예외로 수용하고, YAML에는 S 규칙 10건이 있다. 특히 airport `S9`(`tags`/`info.version`, YAML 308~313)는 문서 메타데이터 정합으로 기재되어 있고 외부 계약 동반 사유가 없어 §6.2 5번의 허용 조건과 맞지 않는다. concierge `S2`/`S3`도 `surface: "*"`로 넓게 등록되어 features export 외부 계약의 범위를 넘어선다.
- 재현: `load_registry(as_of=date(2026, 9, 9))`는 exit 0으로 다음을 출력한다: `S_entries 10 [('geo','S1',...), ..., ('airport','S9','*')]`. 이어서 `openapi-exceptions.md`에도 같은 10건이 예외로 생성된다.
- 영향: 유지자가 “미채택”과 “외부 계약 예외”를 구분할 수 없고, consumer lock의 `openapi.exceptions` 복사 규칙이 SHOULD 비채택을 예외 승인으로 오인할 수 있다. 향후 drift gate가 예외를 정상적인 면제로 취급하면 계층 3 준수 보고가 정본과 달라진다.
- 권고/disposition: 외부 소비자 계약인 항목만 surface를 실제 외부 계약으로 좁혀 유지하고, 나머지 S 항목은 registry와 생성물에서 제거하여 매니페스트 미채택으로 이동한다. 또는 외부 계약 여부를 스키마와 검증 규칙으로 명시하되 §6.2 5번을 ADR과 함께 갱신한다. 현재 candidate에서는 `OPEN`이며 P1이므로 `BLOCK`이다.

### B-P2-03 — flat YAML parser가 숫자·불리언 plain scalar를 문자열로 오인

- 심각도: P2
- 위치: `tools/openapi_exceptions.py:208-214`, `tools/openapi_exceptions.py:373-375`
- 근거: parser는 `null` 외 모든 plain scalar를 문자열로 반환한다. 따라서 문자열 타입 검사가 YAML의 실제 scalar 타입을 검증하지 않는다.
- 재현: canonical YAML의 첫 `owner: kor-travel-geo`를 `owner: 123`으로 바꾼 임시 파일에 `load_registry()`를 실행하면 exit 0이며 `owner`가 `"123"`(Python `str`)로 반환된다.
- 영향: 저장소에서 사람이 잘못된 unquoted number/boolean을 입력해도 7키 문자열 schema 검사를 통과한다. 현재 canonical 값은 정상이나, 생성 Markdown·소비자 매니페스트에 잘못된 타입이 조용히 전파될 수 있다.
- 권고/disposition: 지원 subset의 plain scalar grammar를 문서화한 뒤 숫자·boolean·YAML 특수 scalar를 reject하거나, 허용 문자열은 명시적으로 인용하도록 검사한다. 이 finding은 현재 merge 경계를 직접 깨지는 P2로 `OPEN`이다.

### B-P3-04 — 규칙 표 7열·M10 계층을 보호하는 회귀 시험이 없음

- 심각도: P3
- 위치: `tests/test_openapi_exceptions.py:24-78`
- 근거: focused test는 core ID 집합과 일부 문구만 검사하고, 각 규칙 행의 7열/계층/검사 수단/예외 여부, M10의 별도 계층을 파싱해 고정하지 않는다. 현재 tree를 별도 구조 검사로 실행하면 39행 모두 7열이지만 이 조건은 test suite의 보호 대상이 아니다.
- 영향: 후속 문서 편집에서 표 열을 삭제하거나 M10을 즉시 MUST 목록에 다시 섞어도 focused test가 통과할 수 있다.
- 권고/disposition: escaped pipe를 처리하는 작은 표 검사와 ADR/D-14의 분류 회귀를 추가한다. 현재 기능 오류는 재현되지 않아 P3 `DEFERRED`로 기록한다. owner는 T-301 유지자, gate는 다음 OpenAPI 문서 변경 시 `tools/openapi_exceptions.py --check`와 focused test, 목표 시점은 T-303 착수 전이다.
