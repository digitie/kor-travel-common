# kor-travel-common 통합 실행 계획

이 문서는 단계별 순서·출구·중단 조건을 정의한다. 실행 상태와 선행 관계는 [task 원장](../tasks.md), 개별 수용 기준은 상세 task, 현재 다음 한 작업은 [resume](../resume.md)이 정본이다. 설계는 [architecture](../architecture/README.md), 결정 근거는 [브리프](design-brief.md)와 [ADR 색인](../adr/README.md)을 따른다. 마지막 갱신: 2026-09-06, T-013.

## 1. 이번 인계의 범위

PR #1은 조사·설계·실행 계획·문서 검증 도구의 부트스트랩이다. 로컬 초안을 완성하고 리뷰해 draft PR을 갱신한다. 패키지 구현·소비자 채택·릴리스는 각각 후속 task다. T-003의 SPDX 검사·원문 고지, T-005의 소비자 현재값 검증, T-009 이후 CI·재사용 워크플로가 남아 있으므로 이번 PR의 문서 작업 완료를 Phase 0 전체 완료로 세지 않는다.

초안의 테스트 개수·버전·소비자 상태는 조사 기준 커밋의 관찰이다. [인계 시점 재확인](handoff-verification.md)에는 airport의 이미 병합된 WIP·후속 작업과 남은 CI 실패를 기록했다. 실행 직전 해당 저장소의 코드와 lockfile을 다시 읽고 실제 명령·성공 수·skip·실패를 기록한다. 최신 버전이라고 재인용하려면 공식 원문·조회일을 확인한다.

## 2. 한 에이전트가 한 작업씩 실행하는 규칙

1. `AGENTS.md` → [문서 지도](../README.md) → [resume](../resume.md) → 지정된 상세 task 하나를 읽는다.
2. 진행 중 task가 있고 그 선행이 충족되면 먼저 마무리한다. 선행 미완료 또는 외부 승인이 필요한 상태에서는 의존 작업을 시작하지 않는다.
3. 지정이 없으면 [원장](../tasks.md)의 실행 대기열에서 선행이 모두 DONE이고 외부 선행이 충족된 첫 항목 하나를 선택한다. 같은 조건이면 기반 → 토큰 → UI → Python → 소비자 → 운영 순서와 P0~P3 우선순위를 적용한다.
4. 외부 대기는 BLOCKED와 사유·해제 evidence·담당 저장소를 남긴 뒤 독립적인 다음 항목으로 넘어간다. 시간 경과를 승인으로 해석하지 않는다. 소비자 작업은 해당 저장소의 task·PR로 실행하며 common checkout에서 직접 수정하지 않는다.
5. 수용 기준을 구체화하고 한 task의 변경만 구현·검증·2인 리뷰·수정·재검토한다. 필수 gate가 남으면 DONE으로 옮기지 않는다. task가 여러 독립 PR을 요구하면 착수 전에 하위 task로 나누고 부모는 모두 끝날 때까지 유지한다.
6. 종료할 때 상세 evidence와 원장·resume을 동기화하고 커밋·push·draft PR을 갱신한다. 다음 에이전트는 완료 evidence를 재사용하고 미완료 작업 하나부터 이어 간다.

task 번호·Phase는 분류이며 실행 선행을 대신하지 않는다. 원장의 선행 DAG와 외부 선행이 실제 실행 가능성을 결정한다. 여러 task를 동시에 IN_PROGRESS로 만들지 않는다(이번에 인수한 병렬 초안은 리뷰·잔여를 구분해 정리한다).

## 4. rc 검증과 정식 채택

릴리스 task(T-109·T-212·T-213·T-310·T-311)는 rc 생성과 외부 소비자 **검증 요청**을 소유한다. 소비자 저장소의 담당자가 별도 draft PR에서 rc를 설치·검증하고 결과를 돌려준다. 이 검증은 정식 채택 task(T-410 등)의 DONE을 선행으로 요구하지 않는다. 정식 채택 task는 릴리스 완료 후 정식 자산 URL·lock으로 갱신하고 최종 재검증·merge한다.

이전 minor의 정식 채택은 다음 minor 검증과 구분한다. UI 0.2는 map T-411과 선택한 두 번째 소비자 T-422a 또는 T-432의 0.1 채택이 먼저다. pinvi는 T-020 결정 → T-420 적용 → T-421 토큰 → T-422a(0.1) → T-422b(0.2) → T-422 종료 순서다. 선택 기준·minor별 코드 착수와 peer 계약은 [ADR-013](../adr/013-package-release-execution-contract.md)을 따른다.

따라서 rc 검증 대기 중 릴리스 task는 외부 선행으로 BLOCKED이며, 뒤의 채택 task를 먼저 DONE으로 만드는 순환을 만들지 않는다. 해당 소비자 task의 구현 지침은 검증 담당자가 참고하되 common 에이전트에게 소비자 수정 권한을 부여하지 않는다. 정확한 gate·자산·rollback은 [release](../runbooks/release.md)와 각 상세 task를 따른다.

## 5. 외부 결정과 인계

열린 결정의 목록·기본값은 [브리프 §2](design-brief.md#2-사용자-확인이-필요한-열린-결정기본값으로-진행)가 단일 레지스터다. 특히 권리(L6/L8), 계정(scope), 명시 예외(O-8), 타 저장소 WIP·React 승인은 담당 task의 외부 선행 evidence 없이는 해제하지 않는다. 나머지는 되돌릴 수 있는 문서·설계 기본값으로만 진행한다.

인계에는 현재 commit·PR, 완료한 검증, 실패/NOT_RUN과 영향을 받는 gate, 다음 task·시작 파일, 외부 결정 해제 조건을 남긴다. 로컬 프로세스가 실행 중이라는 이유로 그 산출물을 완료·승인으로 간주하지 않는다.
